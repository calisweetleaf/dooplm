# Dooop-LM falsifier — RESULTS

**Date:** 2026-11-25
**Verdict: DOES NOT TRANSFER (vision-DiT-specific)**

The looped student learns to mimic the teacher at K ≤ K_max — PPL collapses from
~319,000 (untrained) to 226, KL-to-teacher from 9.85 to 2.78 — but extra loops
past K_max make it *worse*, the opposite of the paper's vision-DiT finding.
Per-loop KL rises with k (2.78 → 2.76 → 2.92 → 3.47) and PPL rises with K past
K_max=2 (222 → 264 → 464). The loop does not converge toward the teacher; it
drifts away. The Dooop conversion recipe, as implemented here, is
vision-DiT-specific — at least for this student size, data slice, and step
budget. That is a result, not a failure: the falsifier did its job.

## Setup

- **Teacher:** Qwen/Qwen2.5-0.5B (24 blocks, frozen), loaded in bf16. Held-out
  teacher PPL on wikitext-103 validation: **15.72**.
- **Student:** 2 input blocks (0,1) + ONE shared loop block (12) + 2 output
  blocks (22,23), all initialized from teacher weights; loop-count embedding =
  2-layer MLP (hidden 256) trained from scratch. **74.8M trainable / 210.9M
  total** (teacher 494M). Embed + lm_head frozen (tied).
- **Loss:** per-loop KL of student logits vs teacher logits, k=1..K_max=2,
  w_k=1 (Eq. 9 analog), computed in 64-position chunks (`kl_sum_chunked`,
  log-target KL — exact, see run notes).
- **Data:** wikitext-103-raw-v1 (Salesforce/wikitext mirror), streamed.
  4000 train blocks × 256 tokens (~1.02M tokens), 48 eval blocks.
- **Train:** 400 steps, batch **8** (see run notes — batch 16 OOM'd),
  seq 256, AdamW lr 2e-5 (20-step warmup, cosine to 2e-6), bf16 autocast.
  Final train loss **2.5942** (from 9.6867 at step 1).
- **Eval:** held-out wikitext-103 validation, per-loop KL + PPL at K=1..4.

### Falsifier checks (both fail)

1. **KL decreases with k? NO.** kl_by_loop rises after loop 2: 2.78, 2.76,
   2.92, 3.47. Intermediate-loop outputs do NOT converge toward the teacher.
2. **PPL improves with K past K_max=2? NO.** Best PPL is at K=2 (222.21);
   K=3 (264.01) and K=4 (463.53) are worse.

The student is a good K≤2 mimic and a bad extrapolator. The loop-count
embedding (trained only on k=1,2) has no reason to generalize to k=3,4, and
the shared block drifts with each extra application. This is the exact
opposite of the paper's DiT result (monotone improvement with K), so the
recipe does not transfer as-is to language at this scale.

### Loss trajectory (train, mean per-loop KL)

9.69 (step 1) → 6.16 (20) → 4.03 (40) → 3.13 (80) → 2.96 (100) → 2.76 (200)
→ 2.43 (260) → 2.77 (300) → 2.59 (400). Fast early drop, then a plateau
around 2.4–2.9. Full 400-step history in `results.json` (`train.loss_history`).

## Run notes — what broke and what fixed it

1. **Kernel restart (first run, ~15:3x CST).** The `datasets` non-streaming
   load built a 1.8M-row arrow table for the whole wikitext-103 train split
   and the kernel restarted mid-generation ("Kernel restarting before the
   code finished"). Fix: streaming read (`load_dataset(..., streaming=True)`)
   that stops after enough text is collected, plus bounded single-call
   tokenization (~1.17M tokens, not the full 103M-token train set).
2. **CUDA OOM at the first training step (second run).** The unchunked loss
   held teacher + 2 student logits in fp32 (16×255×151,936 each ≈ 2.49 GB)
   plus full-size softmax/log_softmax temporaries — ~10 GB for the loss
   alone on a 22 GB L4. Fix: `kl_sum_chunked` (64-position chunks,
   log-target KL, exact), bf16 teacher, batch 16 → 8 (within the spec's
   8–16 range), `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, and
   freeing per-loop logits as they are consumed. The chunked KL reproduces
   the unchunked numbers to ~4 decimal places (baseline re-measured after
   the fix matches the pre-fix baseline).
3. **Dirty-kernel OOM (third run).** Re-exec'ing in the same kernel after an
   OOM exception died in `teacher_ppl` with 21.1 GB already allocated:
   IPython retains the failed run's traceback, which holds all its GPU
   tensors alive. Fix: `colab restart-kernel` (verified 0.0 GB allocated
   before the final run). Lesson: after any OOM in a persistent kernel,
   restart the kernel before retrying — do not re-exec into the leaked GPU.
4. **`colab exec -f` leaks the kernel's `-f <conn>.json` flag into
   `sys.argv`.** Fix: `parse_known_args()`. Note: `exec` exits 0 even when
   the remote code raises — verify by output markers and downloaded files,
   never by exit code.
